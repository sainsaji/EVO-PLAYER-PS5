# Performance study, 2026-11-21

What was measured, how, and what to change first. **No console was available for this study.** Every number below
comes from one of three places, named on each line:

- **console log**: `output/logs/evo.log` and `evoplayer-2026110*.log`, written by builds of 2026-11-04 to 11-08
  (17 boots, PS5 Pro, FW 13.60), summarised with `tests/perf/evo_log_perf.py`;
- **host model / host build**: the pinned `ps5-dev` container, branch `local/0.14-integration` (`d3ce98a`);
- **code reading**: a file and line you can check.

A change that touches the console's memory, GPU, decode or timing is off by default or proven identical on the
host. Nothing here says "faster" without a number.

## Ranked findings

### 1. The audio packet ring can take 384 MB of flexible memory for the whole session

**Console log.** 12 of 17 boots report `direct_total=3072MB` (5 report the Pro's 12928 MB; the cause of the 3 GB
boots is not known yet - see *Open questions*). On those boots, every first network playback does this:

```
alloc [decode-open] ... map_fail=0 flex_avail=775MB direct_live=49MB
pb: read-ahead 120s (ring) -> video 7200 pkt / 70 MB, audio 60000 pkt / 256 MB
alloc [play]        ... map_fail=1 flex_avail=389MB direct_live=1073MB
```

**Why.** `sizeReadAhead()` (`core/src/services/PlaybackController.cpp`) asks for a 2 GB video ring and a 384 MB
audio ring at a 120 s buffer (`kVideoRingBytes`/`kAudioRingBytes` x 4). The malloc shim
(`tools/native-app/stubs/malloc_shim.c`, `sh_map`) tries direct memory first for blocks of 1 MB and up, then
**flexible memory**. With 1392 MB of direct memory free, 2 GB fails everywhere (`map_fail=1`), the halved 1 GB fits
in direct memory, and the 384 MB audio ring no longer does, so it lands in flexible memory. The rings are kept
for the life of the process, so the 1 GiB pool runs the rest of the session with 389 MB.

The audio ring is also far larger than the audio needs: the stream above is AAC 2.0 at 256 kbit/s, 3.8 MB for
120 s.

**Host model** (`tests/perf/shim_ring_bench.c`: the real shim, kernel calls mocked as two budgets, replaying the
ring requests). It reproduces the console log exactly, then the fix:

| case | before | after |
|---|---|---|
| 1392 MB direct free, AAC 256k | audio 384 MB, **flex lost 384 MB**, map_fail=1 | audio 16 MB, flex lost 0 |
| 1392 MB direct free, E-AC-3 1.5M | audio 384 MB, flex lost 384 MB | audio 43 MB, flex lost 0 |
| 1392 MB direct free, TrueHD (no bitrate) | audio 384 MB, flex lost 384 MB | audio 192 MB, flex lost 0 |
| 11288 MB direct free (Pro), AAC | 2432 MB direct | 2064 MB direct |
| 200 MB direct free | flex lost 512 MB, map_fail=3 | flex lost 0, rings halve to 128 + 16 MB |

**Fix** (PR `perf/audio-ring-direct-only`): the rings come from a new shim entry, `evo_alloc_direct_only()`, which
returns NULL rather than flexible memory (the ring code already halves on refusal), and the audio ring is sized
from the highest stated bitrate among the file's audio streams (x2, at least 16 MB). An audio stream with no stated
bitrate keeps the full ring. **Risk: low.** A smaller audio ring only changes how far ahead audio is read; the byte
cap is still three quarters of the ring.

### 2. Home posters are decoded on the UI thread, ~42 ms each

**Console log.** `alloc [thumb-start]` / `[thumb-end]` around `extractVideoFrame`: n=19, **avg 41.7 ms, max
50 ms**, inside `screenManager render` (frame 1 of the boot trace took 78 ms). That is two to three dropped frames
per poster at 60 Hz.

**Why.** `LaunchScreen.cpp` called `CoverArtService::getCoverArt()` - synchronous: open the file, decode a frame,
scale - for one recent-shelf tile per frame. The Browse screen already used the worker (`requestCoverArt` +
`pumpAsync`). That path also calls `evo_boot_log_flush()` 3-4 times per poster, each an `fsync` to the USB stick
(`src/evo_boot_log.c`, `bl_drain(1)`); `evo_boot_log.c` itself records a periodic fsync blocking the main loop for
33-83 ms.

**Fix** (PR `perf/home-covers-async`): Home asks the worker, as Browse does, and pumps results each frame. The
fsyncs now run on the worker thread; log enqueue from the UI thread only takes the queue lock, which `bl_drain`
releases before writing. **Risk: low.** Posters appear one by one (the worker pauses 150 ms between local decodes)
instead of one per frame.

The hero backdrop had the same problem: once the cursor settled for 260 ms, `ensureHeroArt()` extracted a
960x540 frame on the render thread. **Fix** (PR `perf/home-hero-async`, on top of the poster PR): the hero is a
worker job too, ahead of posters and behind the Browse preview; the cached poster stands in until it arrives.

### 3. The link keeps every unused section

**Host build.** Objects are compiled with `-ffunction-sections -fdata-sections`, but the `ld.lld` call in
`scripts/package-app.sh` has no `--gc-sections`. With it (same sources, `--ffpfsc --usb-remote`):

| | default | `--gc-sections` |
|---|---|---|
| `eboot.bin` | 51,856,836 B | **47,789,844 B (-4.07 MB, -7.8%)** |
| `.ffpfsc` | 30,277,632 B | 28,508,160 B (-1.77 MB) |
| `.text` | 26,062,848 B | 22,982,656 B (-11.8%) |
| `.eh_frame` | 2,273,964 B | 1,802,472 B |
| undefined dynamic imports | 375 | 340 |

The linker script already `KEEP`s the init/fini arrays and `.eh_frame`; exported symbols stay roots.

**Fix** (PR `perf/gc-sections-flag`): `package-app.sh --gc-sections`, **off by default**. Only a console launch
proves that a fake-signed module with fewer imports still loads and that no section reached only by the loader was
dropped. **Gain:** smaller download and image; less code mapped at load (whether that comes from the flexible pool
is not measured, see 4).

### 4. 39 MB of `.bss`, 17 MB of it FFmpeg FFT tables EVO never uses

**Host build** (`llvm-nm -S` on `llvm-pie.elf`): `.bss` is 38.8 MB. Of that, **16.8 MB** is
`ff_tx_tab_*` - FFmpeg's split-radix tables for transforms up to 2,097,152 points (`libavutil/tx_template.c`,
`SR_POW2_TABLES`). No enabled decoder asks for more than a few thousand. Also static:
`prospero_thumbnail_cache` 7.4 MB, `broker_state` 2.4 MB, `audio_queue` 2.1 MB, `prospero_sub_slot` 2.0 MB.

**Not changed.** Whether untouched `.bss` pages cost flexible memory on this kernel is unknown. Trimming the
tables is also not a build switch: besides `SR_POW2_TABLES`, the init table, `DECL_SR_CODELET` and the codelet
list in `tx_template.c`, the x86 assembly (`libavutil/x86/tx_float.asm`, `cextern tab_ %+ i %+ _float`) and its
`TX_DEF(..., 2097152, ...)` entries in `x86/tx_float_init.c` reference every size up to 2,097,152. Measure first
(*Console checks*, item 3); only if `.bss` costs flexible memory is that patch worth carrying.

### 5. evo_net opens a new connection for every request

**Code reading.** `addons/src/evo_net.c` sends `Connection: close` on every request. A DNS cache (300 s,
`tools/native-app/stubs/evo_dns.c`), TLS session resumption (`s_tls[]`) and parallel range reads for playback
(`media/src/evo_parallel_io.c`) are already there, so the remaining cost is a TCP handshake plus an abbreviated TLS
handshake - two round trips - per API call and poster.

**Host benchmark** (`tests/perf/net_bench.c` against `tests/perf/latency_server.py`, which charges one RTT per new
connection and one per response; plain HTTP, since the host build has no TLS; 40 sequential GETs of a 2 KB JSON):

| | before | after (keep-alive) |
|---|---|---|
| RTT 30 ms | 61.3 ms per request, 46 connections | **31.3 ms**, 3 connections |
| RTT 5 ms | 10.8 ms | **5.5 ms** |
| server with Nagle on, RTT 30 ms | 61.3 ms | 71.7 ms (worse) |

On https the saving is one more round trip (the resumed TLS handshake), not measured here. A chunked body with a
trailer, a 204, a `Connection: close` reply and a pooled connection the server closed while idle all come back
right; the same run is clean under ASan/UBSan.

**Fix** (PR `perf/net-keepalive`): up to 6 idle connections are kept 15 s, and a connection goes back only when the
response ended where it said it would. A reused connection that returns nothing is retried once on a new one. The
Nagle case is the risk: a server that leaves Nagle on and writes header and body separately waits for the client's
delayed ACK on every kept-open request (FreeBSD's delayed ACK is longer than Linux's). nginx, Kestrel
(Jellyfin/Emby), Apache and Node set `TCP_NODELAY`; `/mnt/usb0/evo_net_no_keepalive` switches keep-alive off.

### 6. Every block above 12 KB is its own kernel mapping

**Console log.** The shim's `large=` counter reaches ~10,000 per session and climbs ~20 per second in steady
playback: each is a map and an unmap call (`large_alloc` / `free`).

**Host benchmark** (`shim_ring_bench.c`, the real shim on Linux mmap): malloc + touch every page + free costs
0.01 us for an 8 KB slab block, **14.6 us at 64 KB, 39 us at 256 KB**, 325 us at 2 MB. At ~20 blocks a second that
is under 1 ms per second, about 0.05% of one core. **Not changed:** a block cache would not pay for its risk. The
2 MB cost matters only for churn of big blocks, and the packet rings already took the biggest ones out.

### 7. Startup is already fast

**Console log.** `main()` -> frame loop: **0.39-0.42 s** on 16 boots (one 1.9 s outlier). Nothing big to win here.

### Looked at and dropped

- **Rust.** Nothing found depends on the language. The problems are buffer sizes and which thread does what.
  The SDK has no Rust target, so a part in Rust would need a custom `no_std` target plus proof that the module
  still loads. Not worth it now.
- **`main.c.legacy`** (403 KB). Not compiled, so deleting it does not change the binary; deleted as repo cleanup
  (PR `chore/remove-main-c-legacy`).
- **OpenSSL AVX-512 code** (`ossl_aes_gcm_*_avx512`, ~0.7 MB). Zen 2 has no AVX-512, so this code never runs and
  costs only image size. The library comes prebuilt from pacbrew; rebuilding it adds a build step for 0.7 MB, less
  than a fifth of what `--gc-sections` saves. Not done.

## Open questions

- **Why do most boots report `direct_total=3072MB`?** The Pro package should report 12928 MB (`memory-budget.md`).
  The 3 GB boots are the ones where finding 1 hits. Check what else was running (a game suspended in the
  background?) the next time `mem budget [boot]` shows 3072 MB.
- `evo.log` wrote the Stremio account email in clear at boot (`stremio account: signed in (...)`). Not a
  performance issue; fixed in PR `fix/stremio-log-email`.

## Console checks to run when a PS5 is back

All of them read `evo.log` with `python3 tests/perf/evo_log_perf.py <evo.log>`, before and after, on the same file.

1. **Audio ring** (PR `perf/audio-ring-direct-only`). Play a network file (the Jellyfin HDR10 1080p test file) on a
   boot that reports `direct_total=3072MB`. Expect: `playback start: flex_avail 775 -> ~770 MB`, `map_fail=0`, a
   `pb: read-ahead` line with a small audio cap, no `ring fallback` lines. Then switch to a TrueHD track and seek
   twice: no `ring fallback` lines, audio stays in sync.
2. **Home posters** (PR `perf/home-covers-async`). Boot with 5+ local recent files that have no sidecar image.
   Expect: `Home cover decodes` still logged (now on the worker) and `pace:`/boot frames without 40-80 ms frames
   while posters fill in. Posters should appear within a second or two.
3. **Static memory.** Compare `mem budget [boot] flex_free` between a default build and a `--gc-sections` build.
   If it moves by about the size of the removed code, `.bss`/`.text` cost flexible memory and finding 4 is worth
   doing; if it does not move, they do not.
4. **`--gc-sections` load** (PR `perf/gc-sections-flag`). Build with `--gc-sections`, run the normal cycle
   (`quit` -> `close` -> deploy -> `launch`). Expect `[GAME] started` in ShadowMount's log, the boot trace, Home,
   one local and one network playback, then a clean `quit`. Stop at the first anomaly.
5. **Keep-alive** (PR `perf/net-keepalive`). Open a Jellyfin or Emby library and scroll a shelf of posters, then an
   Xtream category. Expect the shelf to fill faster than on a build without it, the same artwork, and no
   `net: ... failed` lines that are not in a run with `/mnt/usb0/evo_net_no_keepalive` set. Leave EVO on Home
   for a minute, then open a library again: the first request must still work (the idle retry).
6. **Hero backdrop** (PR `perf/home-hero-async`). On Home, move along the recent shelf and stop on a local video:
   the poster shows at once and the sharp frame replaces it shortly after, with no hitch while moving.

## How to re-run the host numbers

```bash
docker compose run --rm ps5-dev ./tests/perf/run_perf.sh                 # ring model, shim churn
docker compose run --rm ps5-dev ./tests/perf/run_net_bench.sh            # keep-alive bench
# inside the container: NET_SRC=path/to/old/evo_net.c RTT_MS=30 NAGLE=1 ./tests/perf/run_net_bench.sh
docker compose run --rm ps5-dev ./scripts/package-app.sh --ffpfsc --usb-remote [--gc-sections]
python3 tests/perf/evo_log_perf.py output/logs/evo.log                    # console log summary
```

Section and symbol sizes: `llvm-size-18 -A` and `llvm-nm -S --size-sort -C` on `output/app/.build/llvm-pie.elf`.
